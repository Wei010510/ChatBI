## 1. 垂直故事

### 1.1 主故事：电商「大促复盘官」

| 维度 | 内容 |
| :--- | :--- |
| 角色 | 电商平台/品牌自营的**运营分析师**（非数据工程师，不会写 SQL） |
| 何时用 | 大促结束后的复盘周：11.12 ~ 11.15，要向运营负责人和类目负责人汇报 |
| 要支持的决策 | ① 这次大促到底打成什么样（GMV/转化/客单/退货）<br>② 哪个渠道、哪个类目拖了后腿<br>③ 和去年同期、和大促前一周比，差在哪<br>④ 下一场活动该加码什么、该收什么 |
| 一句话定位 | 让不会写 SQL 的运营，用一句人话拿到**可信的数 + 看得懂的图 + 一句能复述的解读**；答不了的会明确说答不了，而不是编一个数字。 |

### 1.2 备选故事：日常渠道巡检

- 角色同上，时间从「大促复盘」换成「每天早上的渠道巡检」。
- 差异：日常巡检更依赖**定时/同比**，大促复盘更依赖**多维度拆解 + 活动对照**。
- 为什么主推大促复盘：一次问答能串起「渠道 × 类目 × 时间 × 活动」四个面，一个故事就能把 MVP 能力全演示完；日常巡检容易退化成「看板 + 一句话」。

> **拍板点**：主故事默认按「大促复盘」，若改为「日常巡检」，测例与运营资源都要重写一遍。

## 2. 定向调研

选型原则：五个参考覆盖四种真实形态——**商业 BI 的 AI 模块**（Quick BI、Spotter）、**国内自研 ChatBI 产品**（网易有数）、**开发者的 AI SQL 工具**（Chat2DB）、**开源的语义层 GenBI**（Wren AI）。看它们的**交互取舍**和**明确不做什么**，比看功能列表有用。

### 2.1 阿里云 Quick BI · 智能小Q

**类型**：成熟商业 BI 产品内的 AI 增值模块（多 Agent 组合），最贴近我们要做的「企业级」参照。

**交互要点**

1. 进入对话界面后**先预览/选择数据集**，再在提问框输入问题或点快捷提问。
2. 支持**多轮对话与追问**：问完「华东区本月销量」，可追问「和上月比呢」，再问「下降的主要原因是什么」，逐层下钻。
3. 结果是**表/图 + 解读**一起给，不是只回一段文字。
4. 能力被拆成 5 个 Agent：小Q问数、小Q解读、小Q报告、小Q搭建、小Q洞察，各管一段。
5. PC 端与移动端都有入口，历史对话可在对话列表里回看。

**能力边界**

1. 5 个 Agent 全部是**增值模块，需额外购买**，且只对高级版/专业版开放，个人版不支持——能力被商业分层切开。
2. **归因被单独做成「小Q洞察」Agent**，说明「归因」是重投入能力，不是问数附赠的功能。
3. 准确性靠工程堆：官方口径是百万级专项语料 + 二十余种调优手段，**不是换个大模型就完事**。
4. 权限与定制（嵌入、开放接口、接 Dify/百炼自定义 Agent）属于平台级能力，个人做不动。

**可借鉴到本 MVP 的点**

1. **问数与解读拆成两个 Agent** —— 直接对应我们 P8 的 Query Agent / Insight Agent 双职责。
2. **先选数据集再提问** —— 我们对应为「只在指标/维度字典内提问」，从入口就收窄范围，等于天然的边界控制。
3. **结果＝表 + 图 + 一句解读**，且允许继续追问 —— 这就是我们 PRD 里「可视化与解读的最低体验」。

**待核实**：免费试用额度是否能覆盖完整问数链路；口径歧义时的澄清话术具体长什么样（公开文档未写）。

来源：[Quick BI 智能小Q 概述](https://help.aliyun.com/zh/quick-bi/user-guide/intelligent/)

### 2.2 Chat2DB

**类型**：开源 + 商业版（Pro）的 AI 数据库客户端，代表「NL2SQL 工具」形态。

**交互要点**

1. 连上数据源即可提问，**不需要先手工创建 AI 数据集**，降低前置门槛。
2. 提问之后**直接给数据结果**，不必再手动执行 SQL。
3. `Ctrl/Cmd + K` 唤起 Copilot，交互嵌在编辑器里。
4. 生成 SQL 带**自我纠错**与**准确性评估**，官方称用于抑制幻觉。
5. 中英文自然语言都能问。

**能力边界**

1. 定位是**数据库开发/管理客户端**，面向前台业务的「经营口径」概念基本没有。
2. 安全叙事是「**只取表结构、业务数据不出本机**」，靠不上传数据换取信任。
3. Java 桌面客户端偏重（数百 MB 级），本地形态，不适合当 Web 平台演示。
4. 负责「把话变成 SQL」，**不负责业务解读与运营建议**。

**可借鉴到本 MVP 的点**

1. 「只取结构 / 数据不出域 / 只读」这套安全叙事，可以写进我们的 SQL 只读与安全底线说明。
2. **生成后自评 + 自我纠错**这个模式，对应我们 P7 的「生成 → 只读校验 → 失败重试」链路。
3. 连上就能问的低门槛体验要保留，但必须靠**指标字典**兜住口径，否则门槛降下来、错数也上去了。

**待核实**：开源版本与 Pro 版在自纠错/评估上的差异边界；支持的 SQL 方言清单。

来源：[Chat2DB 官网](https://chat2db-ai.com/)、[更新日志](https://chat2db-ai.com/resources/changelog#120)

### 2.3 Wren AI

**类型**：开源 GenBI（语义层 + Agent），GitHub 上热度最高的开源 BI 类项目之一。

**交互要点**

1. 表面仍是聊天框，但核心主张是「**不是单次 text-to-SQL，而是 Agent 多步推理**」。
2. 明确针对「**第二句问题就崩**」这个行业通病：靠记忆与上下文让追问成立。
3. 分析结果可以**存成 Skill 复用**，下次同类问题自动产出。
4. 开源核心可被其他 Agent 通过 MCP 调用，人和 Agent 走同一套治理。

**能力边界**

1. **开源版没有 UI、没有权限**；SSO、行列级权限、气隙部署都在商业版——开源只给了「引擎」。
2. 反复强调：**聪明模型救不了架构问题**，缺的是「受治理的上下文层」，而不是更好的模型。
3. 不做写入、不直连生产做危险操作，Agent 跑在沙箱里。
4. 主打「定义可信 + 多步作业」，**不做复杂归因/因果推断**。

**可借鉴到本 MVP 的点**

1. **指标字典＝我们的轻量语义层（MDL 的极简版）**，它是准确率天花板，而不是 Prompt 技巧。
2. 「先改定义、再改代码」的治理顺序，正是我们 P12 的迭代原则。
3. 「开源核心 + 商业能力分层」的产品叙事，可以借来支撑我们「平台型工具」的定位说明。

**待核实**：开源仓库 star 数的时效性；MDL 的具体建模写法（是否需要引入该复杂度）。

来源：[Introducing Agentic GenBI](https://www.getwren.ai/post/introducing-agentic-genbi)

### 2.4 ThoughtSpot · Spotter

**类型**：美国头部搜索式 BI 厂商的 AI 分析师 Agent（Spotter 3，2026 年持续迭代），代表「企业级 Agent 分析」的天花板形态。

**交互要点**

1. 对话式提问 + 多轮追问；**Memory 让口径跨会话保持一致**——「revenue」的定义不会每轮重造。
2. **多步深度分析（deep research）**：把问题拆成子分析、识别贡献因子、主动呈现相关模式，而不是单次 NL2SQL。
3. **每一步展示推理过程**，用户可以先核对逻辑再采信结论。
4. 结果图表可交互：点击、下钻、继续追问，官方说法是「no dead end」。
5. **管理员可配置 Spotter instructions**：输出默认格式、歧义问题的处理方式、敏感数据的 guardrails，组织级统一约束 Agent 行为（2026 年 6 月 GA）。

**能力边界**

1. 强依赖自家语义层（worksheet/model）——「Trusted Data In, Confident Decisions Out」，语义层是入场券。
2. 超出标准查询的问题**直接执行代码**（统计建模、自定义计算、情景分析）——能力边界一路扩到 code execution，重投入。
3. **Root-cause 分析是核心卖点之一**——「解释为什么」这种能力，头部厂商才敢主打。
4. 全面企业级：治理、嵌入、通过 MCP 接入自家或三方 Agent。

**可借鉴到本 MVP 的点**

1. **管理员级 instructions / guardrails** —— 对应我们的 `harness/AGENTS.md` + spec：口径、歧义策略、拒答边界应该写成**可配置的文件**，而不是散在 Prompt 里。
2. **展示推理过程** —— 落到我们就是 SQL 可见 + 口径说明，先核对再采信。
3. **Memory 保持口径一致** —— 再次佐证「字典 + 评测」比「更聪明的模型」重要。

**待核实**：Spotter instructions 的配置粒度（能管到多细）；Spotter 3 从 Early Access 到 GA 的实际进度。

来源：[Introducing Spotter](https://www.thoughtspot.com/blog/introducing-spotter-ai-analyst)、[Spotter 3 Meets MCP](https://www.thoughtspot.com/blog/mcp-spotter-in-claude-chatgpt-custom-agents)、[ThoughtSpot 2026-06 Release Notes](https://docs.thoughtspot.com/cloud/26.9.0.cl/26-6-0-cl)

### 2.5 网易有数 · ChatBI

**类型**：国内大厂（网易数帆）基于自研大模型的对话式数据智能助手，与我们目标形态最接近：中文、企业级、主打私有化。

**交互要点**

1. 进入对话后**先介绍可用的数据表**，并给出六类「提问参考」：算数值、看趋势、查明细、TopN、做比较、同环比——问题类型被**显式收敛**。
2. 支持多轮对话；知识库可配置「大家常问」的参考提问。
3. **过程可验证**：把生成的 SQL 回译成自然语言查询条件展示给用户，查询条件与结果的一致性能直接看到。
4. **用户可干预**：查询条件结构化展示后**可手动调整**，用确定性手段修正 AI 的结果。
5. 多端互通（PC / 移动），ChatBI 可插件化嵌入其他系统。

**能力边界**

1. 主打「**可信**」而非「全能」：四大卖点是需求可理解、过程可验证、用户可干预、产品可运营。
2. 安全走**私有化部署 + 行列级权限**，数据不出域——企业级入场券能力。
3. 明确反对直接拿通用大模型做数据分析：数据泄露风险、NL2SQL 准确率低、幻觉捏造字段。
4. 「产品可运营」靠**知识库 + 用户标记正误样本**让 AI 越用越聪明——运营闭环被做成产品的一部分，不是事后补丁。

**可借鉴到本 MVP 的点**

1. **六类提问参考** —— 我们的测例分类（取数 / 对比 / 解读 / 澄清 / 拒答 / 资源）和「快捷提问」可以直接借鉴这种显式收敛。
2. **SQL 回译成自然语言 + 条件可手动改** —— 比我们原计划的「SQL 可见」更进一步：SQL 给懂的人看，**回译给业务看**。建议 PRD 最低体验加一条「查询条件用自然语言复述」。
3. **用户标记正误样本 → 沉淀进知识库** —— 正是 P14 飞轮示意的现实原型：失败问句 → 评测集 → 改字典 / spec。

**待核实**：自研大模型的具体名称与私有化部署门槛；「查明细」类问题在行列级权限下的具体控制细节。

来源：[有数ChatBI 产品页](https://m.sf.163.com/product/ChatBi)、[有数BI 用户手册 · ChatBI 移动端](http://bi.163yun.com/index/manual/p/chatbi-mobile.html)

### 2.6 对本项目的启示

| 结论 | 具体动作 |
| :--- | :--- |
| **保留**：问数 / 解读拆开 | P8 双 Agent，交接字段固定（question / sql / rows / chart / narrative / errors） |
| **保留**：入口先收窄范围 | 只在指标与维度字典内提问，超范围就走拒答 |
| **保留**：字典当地基 | P6 先写 `metrics-dict.md`，口径先于人肉对账，再谈准确率 |
| **保留**：只读 + 数据不出域 | 只读 SQL、禁多语句、超时与行数上限，写进 SDD 安全底线 |
| **保留**：结果＝表 + 简图 + 一句解读 | 作为 PRD「最低体验」，不做花哨可视化 |
| **保留**：查询条件可验证 | 生成 SQL 的同时给**自然语言复述**（有数模式），业务看不懂 SQL 也能核对口径；SQL 本身默认折叠可查 |
| **保留**：口径 / 歧义 / 拒答策略写成配置文件 | Spotter instructions 模式：规则进 `harness/`，不散在 Prompt 里 |
| **保留**：答案可被标记正误 | 有数「用户标记样本 → 知识库」的轻量版，即 P14 飞轮的现实原型 |
| **裁掉**：报表搭建 / 报告生成 / 归因 Agent | Quick BI、Spotter 都在这些能力上重投入（Spotter 甚至做到 code execution），个人 MVP 扛不住，且不是演示必需 |
| **裁掉**：多数据源、权限中台、移动端、Skill 记忆体系 | 属于商业版 / 平台层能力，写进 Out |
| **我们更该强调** | 范围小但**口径可信**、错了**能问清/能拒**、**可评测可回归**、`compose up` 就能跑 |

> 一句话差异点：**不做「什么都能问」，做「问得准、答得起、错了不编」。**

## 3. MVP In / Out

### 3.1 In（每一项都注明「因调研而保留」的依据）

| # | 能力 | 说明 | 依据 |
| :- | :--- | :--- | :--- |
| 1 | 自然语言问数 | 限定在指标/维度字典内，英文/中文口语表述均可 | 五个参考的共同底盘；Quick BI 靠字典+数据集收窄，有数用六类提问参考显式收敛 |
| 2 | 结果表 + 简单图表 + 一句业务解读 | 一个主图即可（柱/线），解读限一句话 | Quick BI「表图解读一体」的最低形态 |
| 3 | 澄清 / 拒答 | 口径歧义要问清；超范围、无数据、要明细导出要拒 | Wren「何时停下来问」；企业级不可编数 |
| 4 | 1 个运营资源接入 | 大促**活动日历**（活动名/时间/力度/渠道），随结果附推荐项 + 一句理由 | 竞品把「归因/行动建议」做成重 Agent，我们只做「轻对照」 |
| 5 | 少量效果评测 | 5 条 case，与测例同源 | 各家都把准确性当工程问题：Quick BI 堆语料、有数做「可验证」、Spotter 配 guardrails——评测是唯一可证伪的手段 |
| 6 | Docker Compose 可部署 | 一条命令起服务 + 数据库，README 可复现 | 平台型工具的最低交付形态 |

### 3.2 Out（明确裁掉，避免范围膨胀）

| 不做 | 理由 |
| :--- | :--- |
| 完整权限中台 / 多租户计费 | Quick BI、Wren 都由商业版本承担，MVP 不碰 |
| 复杂归因 / 因果推断 / 趋势预测 | Quick BI 单独设「小Q洞察」Agent 才做，投入量级不对等；本 MVP 只做数据对照 |
| 报表搭建 / 报告生成 / 看板设计器 | 属于另一条产品线，会稀释主线 |
| 多句长解读 / 自动分析报告 | 解读限一句，避免把「编故事」当能力 |
| 明细数据导出 / 下钻到订单行 | 既是能力膨胀，也是数据安全风险 |
| 跨会话全文检索 / 搜索 / 导出 | 本版只按时间回看会话，不做检索与导出 |
| 报表协作共享 / 订阅 / 定时推送 | 报表是个人沉淀，协作与推送属团队能力 |
| 跨工具 / 跨源拉数、外部附件上传问答 | 只接第一包数据，不做外部数据接入 |
| 无数据接入（L0 库结构）的裸链问答 | 没有库结构就无法保证口径；数据接入是唯一前提 |
| 生产级模型后训练全链路 | 训练语料与调优是厂商级投入，我们只做字典 + 评测 |
| 多模型自动选择编排 | 固定一条链路 + 一个可配模型，换模型只改配置 |
| K8s / 生产级 CI/CD | 与「可演示、可上手」目标不匹配 |
| 多数据源、移动端、流式输出、Skill 记忆体系 | 各参考均放在商业版或后续版本 |

### 3.3 运营资源选型（只选 1 个）

| 候选 | 与故事契合度 | 落地成本 | 判断 |
| :--- | :--- | :--- | :--- |
| **大促活动日历**（推荐） | 高：直接回答「当时做了什么」，复盘必看 | 低：一张结构化表（活动/时间/力度/渠道/类目） | ✅ 选它 |
| 券包与优惠力度清单 | 中：偏执行层，与 GMV 关系需再解释 | 中：需要券维度数据 | 备选 |
| 渠道预算分配表 | 中：偏财务视角 | 中：预算数据不在交易库里 | 备选 |

**推荐理由**：活动日历能把「数字变了」翻译成「那天我们在做什么活动」，是复盘故事里最短的因果桥梁；且它是纯静态结构化数据，不引入外部系统依赖。

**触发规则（待 PRD 细化）**：问题命中「大促期间/活动/为什么」这类意图时，结果侧附 1~2 条活动推荐 + 一句理由；纯数值取数不硬贴。
