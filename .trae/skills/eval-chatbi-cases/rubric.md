# ChatBI 问数评测规则

本规则用于判定用户当场指定的评测文档。先固定规则，再执行题目；不得根据返回结果临时放宽标准，不得把某份题库的题目 ID、数量、专属答案或路径写进本文件。
不允许其他形式对于此文档的修改

## 1. 判定单位与结论

- 每条用例的评测结论只有 **通过** 或 **失败**。
- 每条数值型用例另记 **数据核验状态**：`已核验 / 部分核验 / 未提供基准`；非数值型用例记 `不适用`，不计入数值核验覆盖率。
- **通过**表示所有可判定的通用硬条件、结果类型硬条件及该条文档附加硬条件均满足；它不自动代表未提供基准的数值已被证明正确。
- 任一可判定硬条件失败，该条即为 **失败**。软条件、其它题目的表现和主观加权均不能抵消。
- 数据核验状态必须如实记录，不能用 `未提供基准` 冒充数值正确。

## 2. 返回契约硬门槛

### 2.1 响应包

成功响应必须满足：

- HTTP 请求成功，响应外层包含 `code / message / data / trace_id`。
- `code=0`，`data` 非空，并包含 `message_id / session_id / action / result / clarify / reject`。
- `action ∈ answer / clarify / reject`，三个结果分支满足下表互斥。

| action | 必须非空 | 必须为 null |
| --- | --- | --- |
| answer | result | clarify、reject |
| clarify | clarify | result、reject |
| reject | reject | result、clarify |

以下情况直接失败：HTTP 错误、超时、响应 `code!=0`、`data` 缺失、字段类型错误、未知 `action`、三态互斥被破坏。

### 2.2 结果字段

- `action=answer` 时，`result` 必须包含 `columns / rows / chart / narrative / truncated`。
- 表格读取 `data.result.columns` 与 `data.result.rows`。
- 图表读取 `data.result.chart`；合法结构为 `type / x_field / series`，`type` 只能是 `bar / line`，无图为 `null`。
- 解读读取 `data.result.narrative`。
- `result.truncated=true` 时，必须按截断结果评估；文档要求完整数据或精确全量行数时，截断结果不能视为满足。
- `clarify` 包含 `clarify_id / question / options / allow_free_text / missing`。
- `reject` 包含 `reason_code / message / suggestions / retryable`。

### 2.3 技术失败不等于业务结论

`intent_parse_failed / sql_generate_failed / sql_execute_failed / timeout` 均属于技术执行失败。除非该条文档明确要求技术失败，否则：

- 期望正常出数时，出现上述任一 `reason_code` 均失败。
- 期望业务拒答时，出现上述任一 `reason_code` 仍失败，不能以 `action=reject` 为由放行。
- 技术失败时 `retryable` 应按契约表达可重试；业务拒答不应被当成技术重试场景。

## 3. 评测过程硬约束

发生以下任一情况，对应用例不得判通过：

- 擅自改写问句、替换指标 / 时间窗 / 维度 / 同义词，或增删题目。
- 调换独立题目的执行顺序。
- 偷换澄清选项，或文档未提供答案时擅自选择。
- 多轮题目没有复用同一 `session_id`，或擅自增加 / 省略轮次。
- 只读总表，忽略同 ID 的逐条说明、考察点、补充说明或本地适配要求。
- 用本次生成的 SQL、结构化查询意图或同一链路的另一次输出充当标准答案。
- 为让题目通过而修改系统、题目、规则、缓存、日志或产品配置。

文档自身明确提供「本场 / 本地适用问句」时，逐字使用该版本并记录；这不属于评测者改写。否则只能使用用户问题原句。

## 4. 结果类型硬条件

期望结果类型可能是组合描述，例如「两行对比表 + 柱状图 + 一句解读」。先拆成全部必检项，再逐项判定，不能笼统归成「表」。

### 4.1 表

必须满足：

- `action=answer`，`result` 非空。
- `columns` 非空，每列具有可用的 `key / title / type`；`rows` 为数组。
- 文档要求实际数据时，`rows` 必须非空。
- 文档指定的行数、列名、指标、维度、粒度、排序、TopN、两行 `period`、时间窗及数据内容均为硬条件。

### 4.2 图

必须满足：

- 满足正常 `answer` 前提，`result.chart` 非空。
- `series` 非空，每个系列具有可对应到结果列的 `key` 与可读的 `name`。
- 文档指定柱状 / 折线、X 轴、系列或维度时，逐项一致。
- 单标量图允许 `x_field=null`，不得额外要求它必须有 X 轴字段。
- 文档要求有实际数据时，不能仅凭存在 chart 对象通过，底层 `rows` 也必须有支撑数据。

### 4.3 解读

必须满足：

- `action=answer`，`narrative` 去空白后非空。
- 按项目契约为一句、不超过 60 字。
- 若 `rows` 非空，关键数字、最大 / 最小、涨跌方向和比较对象必须能从本次结果复核。
- 不得出现输入数据中没有的新业务数字，不得做因果归因，不得给行动建议。
- 文档明确要求某项比较或结构结论时，不能只复述一个数字而漏掉该结论。

### 4.4 表+解读

表和解读的全部适用硬条件都必须通过；其中任一项失败，该条失败。若同时要求图，图的硬条件也一并适用。

### 4.5 空结果

- 只有文档明确预期空数据时，`rows=[]` 才可能通过，并必须同时满足 `chart=null、narrative=""`。
- 文档要求实际数据时，空表失败。
- 文档明确期望澄清或业务拒答时，空表仍失败。

### 4.6 澄清

第一步必须满足：

- `action=clarify`，`result/reject=null`。
- `clarify.question` 非空且以人话指出待确认项。
- `clarify_id` 非空；`options / allow_free_text / missing` 符合该条文档。
- 未收到作答前不得出数、直接给结论或自行假定口径。

第二步必须满足：

- 使用第一步返回的同一 `session_id` 与 `clarify_id`。
- 文档指定选项时发送其准确 `value`；指定自由文本时逐字发送 `text`。
- 文档给出第二步期望时，继续按相应结果类型判定；未给出时，只要求接口成功并返回合法三态，如实记录，不擅自补充期望。
- 文档定义了多槽位或多轮澄清时，只按文档给定答案序列继续，直到文档指定的终点。

### 4.7 拒答

必须满足：

- `action=reject`，`result/clarify=null`。
- `reject.message` 非空，以人话说明不可答原因，不是堆叠技术报错。
- `suggestions` 符合文档指定的替代方向；文档未规定方向时，不自行提高要求。
- 除文档明确期待技术失败外，`reason_code ∈ out_of_scope / detail_export / no_data / write_op`。
- 文档指定具体 `reason_code` 时必须精确一致。
- 不得编造业务数字；文档要求说明数据边界日期等已确认事实不算编造。

### 4.8 多轮追问

- 按文档轮次顺序，在同一 `session_id` 中逐轮提问，每轮使用文档确定的原文。
- 每一轮分别检查其期望结果类型与附加要求。
- 后续轮必须保留文档指定的时间窗、指标、维度和口径，只替换本轮明确要求变化的内容。
- 已确认信息被无依据重复澄清、维度丢失、时间窗漂移或退化成错误粒度，均失败。
- 若某一轮发生失败，记录具体轮次；整条多轮用例失败，后续轮次是否继续按 Skill 的异常规则执行并如实标注。

## 5. 数据正确性与核验边界

### 5.1 可以核验的依据

只有评测文档明确提供的以下内容，才可作为该条数据基准：

- 期望值或参考结果。
- 明确的容差与单位。
- 可复算关系或不变量，例如占比合计、两期变化率、排序、TopN 条数、连续日期、最大 / 最小方向。
- 文档指定的维度、行数、列名及逐条附加数据要求。

有上述基准时必须逐项核对；任一可判定项不满足即失败。不得直接查业务库制造基准，也不得把系统自己的 SQL 或查询计划当作答案正确的证据。

### 5.2 数据核验状态

- **已核验**：文档给出的全部数值基准、关系和不变量均已检查并通过。
- **部分核验**：只有部分数值要求存在可判定基准，已判定部分通过，但仍有数值要求缺少基准。
- **未提供基准**：文档只写「答案正确 / 可复现」等原则，未提供任何可判定数值基准或复算关系。
- **不适用**：该条不属于数值型核验范围。

缺少基准本身不额外判失败，但报告必须醒目标注，不能宣称精确数值正确。若用户明确要求所有数值必须有基准并核验，则开跑前列出缺口并暂停确认，不能静默降级。

### 5.3 数值精度与单位

评测前固定使用以下规则，不得看完结果后调整：

1. 文档给定容差时，严格使用文档容差与单位。
2. 文档未给容差时，原始 JSON 数值采用组合容差：`允许误差 = max(0.000001, |期望值| × 0.000001)`。
3. 文档只提供保留 N 位小数的展示值时，按四舍五入比较，允许末位半个单位，即 `0.5 × 10^(-N)`；比较时注明这是展示值容差。
4. 比例与百分数先确认单位再比较；`0.086` 与 `8.6%` 只有在语义确为同一比率时才可换算，并记录换算。
5. 文档要求复算变化率时，使用 `(本期 - 基期) / |基期|`；基期为 0 且文档未定义处理方式时，不编造增长率，记为无法核验该项并说明。
6. 比较前保持原始精度，不先把 API 返回值截断成两位小数再判精确数值。
7. 无法满足文档给定容差即失败；`未提供基准` 只适用于确实没有可判定依据的项目。

## 6. 软条件

以下内容只写入备注，不单独判失败，也不能挽救失败：

- 文案是否优美、是否容易阅读之外的纯风格偏好。
- 图表美观程度。
- 是否命中模板。
- 检索采用 hybrid 还是 lexical。
- 请求耗时长短；超时仍按技术失败处理。

若文档把其中某一项明确列为该条验收硬条件，则仅对该条按文档执行，不推广成全局规则。

## 7. 汇总与计分

设文档实际用例总数为 `N`，通过数为 `P`，失败数为 `F`：

- `N = P + F`
- `通过率 = P / N × 100%`
- 报告若提供百分制分数，`分数 = 通过率`，不得再叠加主观权重。
- 百分比保留一位小数；`N=0` 时不计算通过率，停止评测并询问用户，不写 0 分报告。

设数值型用例总数为 `M`，数据核验状态为已核验的数量为 `V`，部分核验数量为 `K`：

- `数值核验覆盖率 = V / M × 100%`
- 部分核验单独计数，不并入已核验。
- `M=0` 时覆盖率记 `不适用`，不得写成 100%。
- 总条数、分类条数、通过数和核验数全部从当场评测记录重新计算，不写死。
