# ChatBI 问数效果评测

通过后端 HTTP 接口执行用户指定的评测文档，使用固定的 [rubric.md](./rubric.md) 判定，并生成汇总报告。只评测真实问数效果，不做页面联调，不操作浏览器，不 debug，不为提高通过率修改系统。

## 1. 何时使用

- 用户要求「跑问数评测」「按这份评测文档打分」「生成问数效果评测报告」，并点名或要求使用本 Skill。
- 本 Skill 不会每次开聊自动加载，运行时由用户显式点名。

## 2. 何时不使用

- 正在写代码、联调、debug、修改 SDD / Spec、修改题库或本评分规则。
- 做前端浏览器验收，或只问某个功能如何实现。
- 用户尚未提供评测文档，且也不愿意指定一份现有文档时；不得自行出题替代。

## 3. 每场输入与前置条件

开始执行前确认以下事项：

1. **评测文档路径**：必须由用户指定，或在当前请求中直接点名。没有路径就询问，不能默认某份题库。
2. **后端地址**：默认 `http://127.0.0.1:8000`；用户另给地址时使用用户地址。
3. **真实模型**：当前后端进程必须确认以 `USE_MOCK_LLM=false` 运行。不能只读取 `.env` 就推断进程配置已经生效；无法确认时停下问，不得自行改开关后继续。
4. **数值核验要求**：确认用户是否要求所有数值都必须有基准并核验。若有此要求，缺基准时先列出缺口并暂停；否则按评分规则如实标记核验状态。
5. **单步超时**：默认 300 秒，用户另有指定则从用户。不能无限等待。

先请求 `GET /api/health`。只有 HTTP 成功、响应 `code=0` 且 `data.status="ok"` 才继续。该接口只证明服务可用，不得虚构数据库或模型健康结论。

任一前置条件不满足时停止，不发送任何测例。

## 4. 开跑前解析

严格按以下顺序：

1. 完整阅读同目录 [rubric.md](./rubric.md)，本场不得修改。
2. 完整阅读用户指定的评测文档，本场不得修改。
3. 按文档顺序解析每条 `id / 用户问题 / 期望结果类型`，合并同 ID 的逐条说明、考察点、补充说明、指定澄清答案、多轮次及本地适配要求。
4. 缺「用户问题」或「期望结果类型」时停止并询问。
5. 澄清类缺少指定答案，或多轮类缺少完整轮次且无法从文档确定时，开跑前一次问清；不得执行到一半擅自选择。
6. 文档明确提供「本场 / 本地适用问句」时，逐字采用该版本并在报告注明；否则逐字采用用户问题原句，不自行替换档期、时间窗、指标或同义词。
7. 统计并先向用户简要列出：总条数、澄清类条数、多轮类条数、数值型条数、数值基准覆盖情况。缺失信息已补齐后才执行。

解析不得写死题目数量、题目 ID、题库路径或某份题的专属答案。

## 5. HTTP 执行规则

### 5.1 通用

- 按文档顺序逐条执行，每条结束后立即按评分规则记录，不等全部结束后凭印象评分。
- 独立题目首次请求省略 `session_id`，由后端自动创建会话，避免历史串题。
- 一般题目调用 `POST /api/chat/ask`，请求体中的 `question` 严格等于该条已确定的问句原文。
- 只使用真实接口响应判定，不根据日志、SQL 或主观感觉补一个结果。

### 5.2 澄清类

1. 先调用 `POST /api/chat/ask`。
2. 若第一步不是合法澄清，按评分规则记失败，不再虚构第二步，继续下一独立用例。
3. 若第一步合法，保存返回的 `session_id` 与 `clarify.clarify_id`，再调用 `POST /api/chat/clarify`：

```json
{
  "session_id": "第一步返回值",
  "clarify_id": "第一步返回值",
  "answer": { "value": "文档指定选项的准确value" }
}
```

自由文本答案改用：

```json
{
  "session_id": "第一步返回值",
  "clarify_id": "第一步返回值",
  "answer": { "text": "文档指定的自由文本原文" }
}
```

4. 文档指定选项显示文本时，使用该选项真实对应的 `value`，不得把显示文本冒充 `value`。
5. 第二步有明确期望时按相应类型继续判定；没有时只检查成功响应与合法三态，不擅自补期望。
6. 多槽位澄清只按文档给定答案序列继续，直到文档指定终点。

### 5.3 多轮追问

- 第一轮可省略 `session_id`，保存返回值；后续所有轮次复用同一 `session_id`。
- 每轮调用 `POST /api/chat/ask`，问句逐字使用文档对应轮次原文。
- 逐轮记录实际结果、上下文保持情况及该轮硬条件。
- 某轮失败后停止该条后续轮次，未执行轮次如实标注，该条整体失败，然后继续下一独立用例；不得换 session 重试。

## 6. 判定与记录

每条至少记录：

- ID、实际执行的问句原文、期望结果及附加要求。
- 每一步实际 `action`、HTTP 状态和响应 `code`。
- 行数、主要列、`chart.type`、`narrative` 是否为空等必要形态摘要。
- 澄清的 `missing / options` 要点，或拒答的 `reason_code / message` 摘要。
- 每项适用硬条件的过 / 不过及证据。
- 数据核验状态、使用的文档基准、容差和单位换算。
- 软条件仅放备注，不改变通过结论。

形态通过与数值核验必须分开。只有文档提供的期望值、参考结果、容差、复算关系或不变量才能作为数据基准。不得直接查业务库制造基准，不得把本次 SQL、查询计划或同一链路另一次输出当成标准答案。

所有题目结束后，重新从逐条记录计算总数、通过数、失败数、通过率、数值型数量、已核验 / 部分核验 / 未提供基准数量与核验覆盖率。

## 7. 异常处理

- 单条 HTTP 失败或超时：记录 HTTP 状态、响应 `code/message` 和简短 body 摘要，标为失败后继续下一独立用例。
- 响应结构不合法：记为协议错误并判失败，不猜字段含义。
- 技术失败：按评分规则记录具体 `reason_code`，不能当成业务答案或业务拒答。
- 澄清 `clarify_id` 失效：该条澄清流程失败，记录实际错误，不擅自重新提问替代。
- 不中断整场，不反复重试同一题，不改问句碰运气，不因单条失败修改规则。即使后端持续返回错误，也按同一异常规则记录每条独立用例，不擅自跳过题目。

## 8. 全程禁止

- 禁止修改题目原句、期望、逐条说明、评测文档或评分规则。
- 禁止修改算法、前端、后端代码、SDD、Spec、字典、模板、SQL、日志、缓存、Mock 或其它产品开关。
- 禁止直接操作前端或浏览器，禁止 debug、给代码补丁、为失败题目现场修系统。
- 禁止直接查业务库构造标准答案。
- 禁止把完整 `ChainResult`、密钥、连接串或认证请求头写入报告。
- 禁止清空会话或业务数据；评测产生的会话不擅自删除。

## 9. 报告

写入 `开发记录/评测报告-YYYYMMDD.md`。若同名文件已存在，追加 `-HHmmss` 时间后缀，不覆盖已有报告。

### 9.1 开头

写明：

- 评测文档准确路径、后端地址、实际执行总数。
- 通过数、失败数、通过率，分母为评测文档实际用例总数。
- 数值型条数、已核验 / 部分核验 / 未提供基准条数及核验覆盖率。
- 已确认的环境事实：真实模型配置由用户如何确认、health 实际结果、使用的数值容差。
- 不写数据库或模型健康为 ok，不写任何密钥。

### 9.2 主表

至少包含以下列：

| id | 用户问题原文 | 期望结果与附加要求 | 实际 action | 结果形态摘要 | 硬条件过/不过 | 数据核验状态 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |

结果摘要只保留判定所需信息，不粘完整返回体。多轮题目在备注中标注具体失败轮次，必要时按轮次增加子行。

### 9.3 失败摘要

用简短人话列出失败类别与证据，分类从以下选择：

- 出数
- 数据核对
- 澄清
- 多轮上下文
- 业务拒答
- 技术执行失败
- 协议错误

只陈述证据，不提供修复补丁，不擅自修改系统。报告末尾核对总数与各项比例，确保和逐条记录一致。
