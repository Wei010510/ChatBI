## 1. 这条 Skill 评测什么

评测已经在本机运行的 ChatBI 的真实问数效果：问题能不能答、答案形态是否完整、可核验的数据是否正确、该澄清时是否先澄清、不该答时是否业务拒答、多轮追问是否沿用上文。

它不是联调工具，不检查页面能不能打开，不模仿人点击前端，不 debug，不修代码，不为了让题目通过而调整系统。

调用方式：由用户指定一份评测文档 → 逐字读取其中的用例与判定要求 → 通过后端 HTTP 接口逐条执行 → 严格按预先写好的 `rubric.md` 和该条文档的附加硬条件判定 → 输出汇总报告。

## 2. 创建时先核对本项目真实契约

先读：
- `docs/SDD-后端.md` §2.1、§2.2、§6：统一响应包、`POST /api/chat/ask`、`POST /api/chat/clarify`、真实模型开关。
- `docs/SDD-算法应用.md` §7.4、§2.10：`ChainResult` 三态互斥与 `narrative` 约束。

写规则时必须使用本项目字段，不要照搬其它系统的 `table / insight`：
- 成功响应外层为 `{code, message, data, trace_id}`，`code=0` 才进入用例判定；`data` 另含 `message_id`、`session_id`。
- 表格是 `data.result.columns + data.result.rows`。
- 图表是 `data.result.chart`，结构含 `type / x_field / series`，只会是 `bar / line` 或 `null`；单标量图允许 `x_field=null`。
- 解读是 `data.result.narrative`，不是 `insight`。
- `action=answer` 时 `result` 非空，`clarify/reject=null`；空数据也可以是 `answer`，表现为 `rows=[]、chart=null、narrative=""`。
- `action=clarify` 时 `clarify` 非空且 `result/reject=null`，字段含 `clarify_id / question / options / allow_free_text / missing`。
- `action=reject` 时 `reject` 非空且 `result/clarify=null`，字段含 `reason_code / message / suggestions / retryable`。
- 澄清第二步使用同一个 `session_id` 和第一步返回的 `clarify_id`，请求体为 `{session_id, clarify_id, answer}`；选项答案用 `answer={value: 对应value}`，自由文本用 `answer={text: 文档原文}`。
- 独立用例首次 `ask` 可省略 `session_id`，由后端自动建会话；不要调用不存在的 `/api/conversations`。
- 本项目真实模型开关是 `USE_MOCK_LLM=false`，不是 `MOCK_MODE`。
- 本项目没有 `CLARIFY_ENABLED` 开关，不得捏造这个前置项，也不得为评测新增产品开关。
- `GET /api/health` 当前只证明服务可用，成功标准为 HTTP 成功、响应 `code=0` 且 `data.status="ok"`；它没有 `db`、`llm` 健康字段，报告不得虚构这两项检查。

## 3. rubric.md：先固定判定规则

### 3.1 每条用例的通用硬门槛

以下任一情况即失败，不能用其它优点抵消：
- HTTP 请求失败、超时、响应 `code!=0`、`data` 缺失或返回体不符合上述三态互斥。
- 实际 `action` 与题目期望不符；期望正常出数却得到澄清或拒答，期望澄清或拒答却直接出数。
- 技术失败冒充业务答案或业务拒答。`intent_parse_failed / sql_generate_failed / sql_execute_failed / timeout` 都按执行失败处理；除非文档该条明确要求技术失败，否则不能算通过。
- 擅自改写问句、增删题目、调换独立题目的顺序、偷换澄清选项、为多轮题目新建会话，均属于评测过程违规；已产生的对应结果不得判通过。
- 题目「逐条说明 / 考察点 / 补充说明 / 本地适配说明」里写了更细要求的，这些要求与同 ID 的期望结果类型一起构成硬条件，不能只读总表后忽略。

### 3.2 按期望结果类型判定

期望类型可能写成组合描述，例如「两行对比表 + 柱状图 + 一句解读」。必须拆出全部要求逐项检查，不能笼统归成「表」后放行。

- **表**：`action=answer`，`result` 非空，`columns` 非空且 `rows` 为数组；文档要求有数据时 `rows` 必须非空。行数、列名、维度、排序、TopN、两行 `period` 等以该条文档为硬条件。
- **图**：满足正常 `answer` 前提，且 `result.chart` 非空、`series` 非空；文档指定柱状 / 折线、X 轴或系列时逐项一致。不得额外要求单标量图必须有 `x_field`。
- **解读**：`action=answer` 且 `narrative` 非空。若本次有数据行，解读中的关键数字、最大 / 最小、涨跌方向和比较对象必须能从本次 `rows` 复核；不得出现输入数据中没有的新业务数字，不得做因果归因或给行动建议。项目契约要求一句、不超过 60 字。
- **表+解读**：表与解读的硬条件都要过；不能只有数字复述却漏掉题目明确要求的比较结论。
- **空结果**：只有文档明确预期空数据时才允许 `rows=[]` 通过，并检查 `chart=null、narrative=""`；文档要求实际数据或明确拒答时，空表不能算过。
- **澄清**：第一步 `ask` 必须是 `action=clarify`，`result/reject=null`，`question` 是人话，`options / allow_free_text / missing` 符合该条要求，未作答前不得出数。直接给数、直接给结论或自行假定口径均失败。随后按文档指定的选项 / 自由文本调用 `clarify`；第二步有明确期望就继续按对应类型判定，没有则只要求接口成功且返回合法三态，并如实记录，不擅自补期望。
- **拒答**：必须是 `action=reject`，`result/clarify=null`，`message` 非空且说明人话原因，`suggestions` 符合文档的替代方向要求。除文档明确期待技术失败外，`reason_code` 必须属于业务拒答 `out_of_scope / detail_export / no_data / write_op`，文档指定具体 reason_code 时还要精确一致。不得编造业务数字；文档要求说明数据边界日期等事实不算编造。
- **多轮追问**：按文档轮次在同一 `session_id` 中依次 `ask`，每轮问句逐字使用文档原文。逐轮检查期望形态，并检查后续轮是否保留文档指定的时间窗、维度、口径，只替换本轮指定内容；已确认的信息被重复澄清、维度丢失或退化成错误粒度均失败。

### 3.3 「形态对」与「数值对」分开，禁止假装核验

每条数值型用例都要有两类结论：
1. **契约与形态结论**：上述硬条件是否通过。
2. **数据核验结论**：`已核验 / 部分核验 / 未提供基准`。

- 评测文档明确给出期望值、参考结果、容差、可复算关系或不变量时，必须逐项核对；不满足即该条失败。例如 TopN 条数与排序、占比合计、两期变化率、最大 / 最小方向、连续日期、指定维度与行数等，按题目要求检查。
- 只有文档提供的基准才能判定精确数值是否标准正确。不得把系统本次生成的 SQL、`query_spec` 或另一段相同链路输出当成标准答案，不得为了制造基准而绕开 Skill 直接查业务库。
- 文档只写「答案正确 / 可复现」却没有期望值、参考结果或可复算关系时，不得猜测基准，也不得宣称「数值正确」。该条可以按已可判定的硬条件判过，但报告必须醒目标注「数值未提供基准，未核验」。
- 若用户明确要求「所有数值必须有基准并核验」，则缺少基准时开跑前列出问题并暂停确认，而不是静默降级。
- 数值比较要在 `rubric.md` 预先写明精度规则：原始数值按文档容差；文档未给容差时使用确定的数值容差，展示值按四舍五入后的末位精度比较，并在报告说明，不得看结果临时放宽。

### 3.4 过、不过与计分

- 每条用例只有 `通过 / 失败` 两种评测结论；另设 `数据核验状态`，不能用「未核验」冒充数值正确。
- 所有可判定的通用硬条件、类型硬条件、该条文档附加硬条件均满足，才算通过。任何一项硬条件失败，该条即失败。
- 软条件只进备注，不单独判失败，也不能挽救失败：文案是否优美、图表美观程度、模板是否命中、检索走 hybrid 还是 lexical、耗时长短。
- 通过率 = `通过条数 / 文档实际用例总数 × 100%`；若报告给百分制分数，分数只能等于该通过率，不能再用主观加权分掩盖失败。
- 同时报告数值核验覆盖率 = `数据核验状态为已核验的数值型条数 / 数值型总条数 × 100%`；部分核验单独计数，不并入已核验。
- 总条数、分类条数全部从用户当场指定的文档计算，不写死任何数量或题目 ID。

## 4. SKILL.md 必须写明的使用方式

### 何时使用
- 用户说「跑问数评测」「按这份评测文档打分」「生成问数效果评测报告」，并点名或要求使用本 Skill。

### 何时不使用
- 正在写代码、联调、debug、改 SDD / Spec、改题库、改 rubric、做前端浏览器验收，或只问某个功能怎么实现时。
- 本 Skill 不会每次开聊自动加载；运行时由用户显式点名。

### 每场必须由用户指定或确认
- 评测文档路径；没有路径就先问，不能默认写死 `docs/测例.md`，也不能自己另出题。
- 后端地址，默认 `http://127.0.0.1:8000`；用户另给地址就用用户的。
- 当前后端进程确实以 `USE_MOCK_LLM=false` 运行。不能只看到 `.env` 写着 false 就推断运行进程已生效；无法确认则停下问，不得自行改开关后接着跑。
- 单步 HTTP 超时默认 300 秒，用户另有指定则从用户；问数可能较慢，但不能无限等待。

### 开跑前解析与检查
1. 先读同目录 `rubric.md`，再读用户指定的评测文档；本次运行期间两者都不得修改。
2. 原样解析每条 `id / 用户问题 / 期望结果类型`，并合并同 ID 的逐条说明、考察点、补充说明、指定澄清答案、多轮次与本地适配要求。
3. 缺「用户问题」或「期望结果类型」就停下问；澄清类缺少指定答案、多轮类缺少完整轮次且无法从文档确定时，也在开跑前一次问清，不得跑到一半擅自选择。
4. 文档自身明确给出「本场 / 本地适用问句」时，逐字使用该适用版本并在报告注明；否则只能使用用户问题原句，不得自行替换档期、时间窗、指标或同义词。
5. 先做健康检查；不满足真实契约或真实模型前置条件则停止，不发任何测例。
6. 开跑前简要列出解析到的总条数、需要澄清 / 多轮的条数、数值基准覆盖情况；缺失信息已补齐后才执行。

### 执行步骤
1. 按文档顺序逐条执行。独立题目各自省略 `session_id` 首次 `ask`，避免历史串题；多轮追问和澄清第二步必须复用对应 `session_id`。
2. 一般题目调用 `POST /api/chat/ask`，`question` 严格等于该条文档确定的问句原文。
3. 澄清类执行 `ask → clarify`；多轮类在同一 session 逐轮 `ask`，不擅自增加轮次。
4. 每条结束后立即按 `rubric.md` 记录硬条件、附加条件和数据核验状态，不等全部跑完再凭印象打分。
5. 单条 HTTP 失败或超时时，记录 HTTP 状态、`code/message` 和简短 body 摘要，标为失败后继续下一条；不中断整场，不反复重试同一题，不改问句碰碰运气。
6. 所有题目完成后重新核算总条数、通过数、失败数、通过率与数值核验覆盖率，再写报告。

### 全程禁止
- 禁止修改题目原句、期望、逐条说明、评测文档、`rubric.md`。
- 禁止改算法 / 前端 / 后端代码、SDD、Spec、字典、模板、SQL、日志、缓存、Mock 或其它产品开关。
- 禁止直接操作前端或浏览器，禁止 debug、给代码补丁、为失败题目现场修系统。
- 禁止把完整 `ChainResult`、密钥、连接串、请求头认证信息写进报告。
- 禁止清空会话或业务数据；评测产生的会话不擅自删除。

## 5. 报告约定

路径：`开发记录/评测报告-YYYYMMDD.md`；若同名文件已存在，加时间后缀，不覆盖已有报告。

报告开头写：
- 本次评测文档的准确路径、后端地址、实际用例总数。
- 通过数、失败数、通过率；数值型条数、已核验 / 部分核验 / 未提供基准条数与核验覆盖率。
- 环境只写已确认事实：`USE_MOCK_LLM=false` 是否已由用户确认、health 实际结果；不得写 db / llm 为 ok，不写任何密钥。

主表至少包含：
`id｜用户问题原文｜期望结果与附加要求｜实际 action｜结果形态摘要｜硬条件过/不过｜数据核验状态｜备注`

结果形态摘要只写必要信息，如行数、主要列、chart.type、narrative 是否为空、clarify 问题点、reject.reason_code，不粘完整返回体。

失败用例再用短清单写人话：卡在「出数 / 数据核对 / 澄清 / 多轮上下文 / 业务拒答 / 技术执行失败 / 协议错误」哪一类，依据是什么。只陈述证据，不给修复补丁，不擅自改系统。

## 6. 创建完成后的静态自查与交付

创建完成后只检查：
- 是否先写了完整 `rubric.md`，再写 `SKILL.md`，而不是空 Skill 留待运行时临时决定评分。
- 是否没有写死题库路径、题目数量、题目 ID 或某份题的专属答案。
- 是否使用了本项目真实字段、接口和开关，没有 `table / insight / MOCK_MODE / CLARIFY_ENABLED / /api/conversations` 等错误契约。
- 是否明确区分形态通过与数值核验，并包含多轮、澄清、业务拒答、技术失败、空结果和题目附加硬条件。
- 是否没有调用问数接口、没有跑评测、没有改其它文件。

最后告诉我 Skill 路径，并说明：不会每次开聊自动加载；使用时要点名这条 Skill，并告诉它评测文档路径。此次只创建 Skill，不运行评测。
