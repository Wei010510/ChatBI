# 05·P4 写 SDD Prompt

---

PRD已经定了，接下来我觉得可以写SDD了。SDD是技术侧的设计文档，后面就要按它Coding，所以这一步会直接影响开发质量。请先把方案写完整、写清楚，决策点要暴露出来，方便后面反复修改，不要藏在空话里面。

先把这些读完再动笔，别空写：

- `docs/PRD.md`（需求基准，SDD里的能力必须对得上，不能少做PRD要的，也不能把PRD明确不做的做进来）
- `docs/测例.md`（问题验收题，算法和数据方案要能支撑这些问题跑起来）
- `开发记录/01-实操方向-企业级ChatBI与电商落地.md`（方向背景，当背景看）

调研纪要可以扫一眼当背景，但不要把某个岗位、某张业务资源写成平台架构的前提。电商大促复盘只是第一包验收数据/问法，不是系统只为这一个场景服务。

我已经定了的原则，按这个写，别自己改主意：

1. SDD不要堆在一个文件里。总览一份，前端技术方案一份，后端技术方案一份，算法应用方案一份，后面我要按模块逐个改。四份之间用路径互相引用，内容不要复制粘贴成四份重复文档，三部分怎么衔接，写在总览里，不要再拆第五份。改某一个方案的时候，先改那一份，再回头改总览里对上的衔接和对照表
2. 所有功能落点必须能对上PRD。PRD里F1~F9、交互明细、In/Out、版本演示要有/可暂缓，在SDD里都要有对应。对不上的别写，PRD没有的别擅自加
3. 登录鉴权本版本演示可暂缓；架构上可以预留，本版接单用户提问和报表跑通即可，不要做成完整权限中台
4. 算法应用方案是重点。大家都知道ChatBI会用大模型做Text2SQL，但你必须把具体实操链路写出来：每一步做什么、输入是什么、输出是什么、失败或需要澄清/拒答时从哪一步出去、下一步谁接。不要只写一句「用LLM生成SQL」一句话
5. 前端负责页面和交互怎么落地，后端负责接口、存储、查数执行、部署，算法负责问句理解到出结果这条智能链路。报表沉淀（一键保存、再打开不重查）要前后端一起设计，别只写在前篇
6. 框架、模块怎么拆、目录怎么分，要给出明确结论和理由，写死一版便于后面Coding。不要并列三个方案让我猜
7. 本版用Docker Compose能起服务、浏览器打开就能用

只产出这四个文件，不要合并成 `docs/SDD.md`：

- `docs/SDD-总览.md`
- `docs/SDD-前端.md`
- `docs/SDD-后端.md`
- `docs/SDD-算法应用.md`

需要指标/数据约定大纲的话，可以另外写 `docs/metrics-dictionary.md`，但别写业务代码，也别改 PRD 和测例。

各文件请覆盖这些，章节名你可以排，但别漏。

一、docs/SDD-总览.md
1. 技术方案一句话：系统由哪几块构成，一次问数在三部分之间怎么走完
2. 逻辑架构图（可用mermaid）：前端、后端、算法应用、数据，四者关系一眼能看懂
3. 和PRD的对照表：PRD每个功能（F1~F9）分别由前端/后端/算法谁主责、谁配合，本版演示要有还是暂缓
4. 非目标：对齐PRD的Out和暂缓，写明架构上故意不做或本版不做的
5. 仓库目录树草案，跟模块能对上
6. 三份方案文档的路径，以及它们各自负责什么
7. 三部分怎么衔接（单独写清，不要散落到另外三份里）：
- 一次完整问数：用户在前端提问 → 后端如何接到算法 → 算法每一步怎么走 → 结果如何回到前端展示
- 一次澄清：算法认为要问 → 前端如何出选项 → 用户确认后如何带着口径再进链路，确认前不出数
- 一次存报表：前端点保存 → 后端把哪些字段落库 → 再次打开为什么不重新走Text2SQL

二、docs/SDD-前端.md
按PRD交互来设计，不要重新发明一套产品。至少写清：
1. 页面和信息架构：对话页、结果区、报表列表、报表查看，怎么进怎么回
2. 每个本版演示要有的功能，前端怎么实现交互（提问、过程提示、表/图/一句解读、澄清选项、拒答说明、存为报表、报表列表/打开/改名/删除、当前会话记录）
3. 前端调用哪些后端接口（路径、关键入参出参、错误怎么展示），先把契约写清楚
4. 图表怎么出：前端画还是后端给配置，和算法产出怎么对上
5. 鉴权本版怎么处理（例如先无登录），正式上线预留什么，别假装没有这回事
6. 文首注明：接口契约以后端文档为准，若有冲突先改总览衔接再改本文件

三、docs/SDD-后端.md
1. 服务怎么拆、职责边界（网关/对话/报表/数据查询等，定一版并写死）
2. 接口清单：对齐前端契约，覆盖问数、澄清确认后续查、拒答、存报表、报表CRUD、拉当前会话
3. 存储：对话记录（本版当前会话）、已存报表（口径+图表+解读，再次打开不重新查询）怎么存，存什么字段
4. 数据层：第一包用电商大促复盘相关的模拟数据把测例跑通；平台本身按「已配置范围」查数，不要写死成只能服务某一个岗位
5. 查询执行：SQL或受控查询在哪执行、超时/空结果/执行失败怎么回给前端和算法
6. 部署：Docker Compose 拓扑、谁依赖谁、浏览器访问哪个地址
7. 文首注明：算法链路以算法应用文档为准，本文件只写如何调用、如何落库、如何返回

四、docs/SDD-算法应用.md（详细写，这是深度所在）
1. 先写死总链路。建议按实际可跑的步骤拆，例如：理解问题 → 判断范围/口径是否清楚 → 不清楚则澄清或拒答并结束本轮查询 → 清楚则对齐指标与维度 → 生成SQL → 执行 → 校验结果（防编数、防口径乱跳） → 生成表数据与图表配置 → 生成一句业务解读。你可以调整步骤，但每一步都要有，不能跳着写
2. 每一步写：谁做（模型/规则/工具）、输入、输出、成功去哪、失败去哪。澄清、拒答必须是链路上的正式出口，不是事后补一句
3. 对比类问题（同比、环比、前后时段）在链路上怎么走，和普通取数有什么不同
4. 模块怎么拆：查数和解读要不要分开、状态/交接字段是什么（问题、口径、SQL、结果行、图表配置、解读、错误码等），写死一份，前后端都按这份接
5. 用什么编排/框架（写死一个，并说明为什么适合这条链路；不要空泛罗列）
6. 第一包测例怎么被这条链路支撑：不必逐条设计实现，但要说明 T09 澄清、T10 拒答、取数/对比/解读在链路上分别落在哪几步
7. 和「已配置范围」的关系：范围从哪来（配置/字典这类机制），算法如何知道什么能答、什么必须拒，不要靠模型自己猜表

写完我自己拿着这四份文档要能：对照PRD判断每个功能技术上落在哪一份里；按总览里的衔接想象一次问数怎么跑完；按某一份方案单独改某一块，而不用翻一整本。不要只有概念没有交接物。
