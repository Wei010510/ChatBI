## 五、需要新增或修改的部署文件

**1. 根目录 `.gitignore`**

- 忽略各级真实 `.env`、`.env.*`，但保留 `.env.example` 和 `.env.production.example` 模板。

- 首次 `git add` 前检查真实连接串、Key、会话导出和本地调试文件不会被提交。

**2. 根目录 `.dockerignore`**

- 排除 `.git`、真实环境文件、依赖目录、构建产物、Python 缓存和本地测试产物。
- 保留 backend、algorithm、frontend 源码及后端语义资源。
- 当前 build context 是根目录，所以只需要这一份真正生效的 `.dockerignore`；不要再造不会被使用的 `backend/.dockerignore`。

**3. `backend/Dockerfile`**

- 修正为完整源码可用后再安装 backend/algorithm 本地项目依赖。
- 保留单 FastAPI 服务，不让算法直连数据库。
- 镜像内不得包含 `.env`、`.env.production` 或任何真实密钥文件。

**4. 新增 `frontend/Dockerfile`**

- 使用现有 `frontend/package-lock.json` 执行 `npm ci`。
- 执行 `npm run build`，再用 Nginx 托管生成的 `dist`。
- 前端仍通过同源 `/api` 访问后端，不写死服务器 IP 或 `localhost:8000`。

**5. 修改 `backend/nginx.conf`**

- 保留 SPA fallback 和 `/api` 到 `api:8000` 的反向代理。
- 将相关代理读取超时配置为 300 秒，与现有前端请求上限一致。
- 不顺手改页面、接口路径或 CORS 业务逻辑。

**6. 新增 `backend/docker-compose.production.yml`**

- 只定义 api/web，保留本地 `backend/docker-compose.yml` 的 db 拓扑。
- api 使用项目根目录作为 build context，web 使用新的前端 Dockerfile。
- 仅 web 对宿主机暴露 80；api 只暴露给 Compose 内网。
- 显式设置 `USE_MOCK_LLM=false`；关键数据库和模型配置缺失时应在启动前明确报错，不静默使用 Mock 或错误默认值。
- 配置 api 健康检查、web 对 api 的依赖以及 `restart: unless-stopped`。

**7. 新增 `backend/.env.production.example`**

- 只提交变量名、占位符和必要注释，不放任何真实值。
- 覆盖现有 `DATABASE_URL`、可选只读/元数据库连接、`DATA_SCHEMA=public`、`LLM_BASE_URL`、`LLM_API_KEY`、三档模型、Embedding 配置和 `EMBED_DIM`。
- 服务器真实文件为 `backend/.env.production`，权限 600，只放服务器，不进入 Git、rsync 删除范围或 Docker build context。

**8. 新增 `.github/workflows/deploy.yml`**

- 支持推送 `main` 和 `workflow_dispatch` 手动触发，并设置并发锁避免同时部署。

- 使用专用部署密钥和 known-host 校验，不要把我的个人私钥放进 GitHub。
- 通过 SSH/rsync 同步代码到 `/opt/chatbi`，明确排除所有真实 env；不得使用会删除服务器 env 的 `--delete-excluded`。
- 远端执行生产 Compose 的构建、启动和健康检查。失败时工作流必须失败，只输出脱敏后的状态和日志。
- 首版不引入镜像仓库、K8s、复杂回滚体系或额外监控中台。

**第 3 步：服务器首次初始化**
